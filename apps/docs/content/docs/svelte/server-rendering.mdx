ui-sdk parts render HTML with Svelte's server renderer. Their initial attributes include ARIA state and the group's tab stop.

## Render the Initial State

```svelte
<script lang="ts">
  import { Toggle } from "@ui-sdk/svelte/toggle"
</script>

<Toggle defaultPressed>Bold</Toggle>
```

The server sends a button with `aria-pressed="true"`. It can toggle after hydration. Native HTML behavior, such as submitting a form, can work before hydration.

## Read Browser Values After Mount

The server does not know the browser’s language. Start with the same placeholder on the server and client, then read the language after mount:

```svelte
<script lang="ts">
  import { onMount } from "svelte"

  let language = $state("")
  onMount(() => {
    language = navigator.language
  })
</script>

<p>{language || "Loading language…"}</p>
```

Both initial renders show “Loading language…”. Once mounted, the paragraph shows the browser’s language. Read other browser-only values in the same place, or in an event handler.

## Saved Preferences and Storage

Preferences like a color scheme or an emoji skin tone are saved in the browser, so the server can't render them. [Preferences](/docs/behaviors/preferences) covers the preferences themselves; this is how they fit server rendering.

### Show Them Before Hydration

Render `Preferences` around your app. On the server it renders one inline script as its first child, which puts every saved value on its `data-*` attribute as the page loads, before Svelte hydrates, so CSS that selects those attributes is right from the first paint:

```svelte title="app.svelte"
<script lang="ts">
  import { Preferences } from "@ui-sdk/svelte/preferences"
  import Page from "./page.svelte"
  import { colorScheme, skinTone } from "./preferences"
</script>

<Preferences preferences={[colorScheme, skinTone]}>
  <Page />
</Preferences>
```

A preference made with `global: true` goes on `<html>` instead. Pass `nonce` if your Content Security Policy only allows inline scripts with one.

Content that reads a preference through `usePreference` renders the default on the server and the saved value once mounted. Style by the attribute instead wherever the first paint has to be right, as [Style by Preferences](/docs/behaviors/preferences#style-by-preferences) shows.

### Read a Cookie on the Server

A preference kept in a cookie can render on the server too, content included. Read the request's `Cookie` header on the server, however your server or framework gives you the request, and pass it to your app as a prop, like `render(App, { props: { cookie } })`. Create the preference in the component and share it through context, so each request gets its own, as [Give Each Request Its Own State](#give-each-request-its-own-state) explains:

```svelte title="app.svelte"
<script lang="ts">
  import { createCookieStorage, createPreference } from "@ui-sdk/core"
  import { Preferences } from "@ui-sdk/svelte/preferences"
  import { setContext } from "svelte"
  import Page from "./page.svelte"

  let { cookie }: { cookie: string | null } = $props()
  // svelte-ignore state_referenced_locally
  const skinTone = createPreference({
    values: ["default", "light", "medium", "dark"],
    defaultValue: "default",
    attribute: "data-skin-tone",
    storage: createCookieStorage("skin-tone", { cookie }),
  })
  setContext("skin-tone", skinTone)
</script>

<Preferences preferences={[skinTone]}>
  <Page />
</Preferences>
```

The server reads the value from `cookie`, and the browser from `document.cookie`, so both render it and hydration matches.

### Render the Storage Script Yourself

`Preferences` is the usual way. For one component that keeps its own value, like a toolbar's density, a storage's `script` returns the same kind of inline script for a single element. Render it right after the element, since it writes to the element right before it:

```svelte title="toolbar.svelte"
<script lang="ts">
  import { createLocalStorage } from "@ui-sdk/core"

  let { children } = $props()

  const density = createLocalStorage("density")
  const script = density.script({ attribute: "data-density", values: ["comfortable", "compact"] })
  let element: HTMLDivElement | undefined = $state()
  // The script is in the server's HTML until then.
  let mounted = $state(false)
  // Only the server renders the attribute. Svelte writes attributes while it
  // hydrates, which would put the server's value back over the saved one.
  const server = typeof window === "undefined" ? { "data-density": "comfortable" } : {}

  $effect(() => {
    element?.setAttribute("data-density", density.get() === "compact" ? "compact" : "comfortable")
    mounted = true
  })
</script>

<div {...server} bind:this={element}>{@render children()}</div>
{#if !mounted && script}{@html `<script>${script}<\/script>`}{/if}
```

- **Only from the server.** The browser never runs a script Svelte inserts, so drop it once mounted.
- **Set the attribute yourself.** Svelte writes attributes while hydrating, so render this one on the server only and set it from an effect, as above, or hydration puts the server's value back for a moment.
- **Shared by ID.** Every script with the same storage kind and ID reads the storage once, however many elements render it, and the scripts are identical, so compression shrinks the repeats.
- **Only safe values.** Any script on your site can write the saved value, so `script` only sets attributes that start with `data-`, and only to one of `values`.
- **Not for cookies.** A cookie storage's `script` returns undefined, since the server reads the cookie and renders the value itself.

To run before the page's content at all, render `preferencesScript([...])` from `@ui-sdk/core` in `<head>` yourself, like with `<svelte:head>`. Only global preferences make sense there, since the others go on the script's parent element.

## Keep IDs and Values Consistent

Use the same initial component values on the server and client. For example, do not render an open dialog on the server and a closed one for the first client render.

Parts generate IDs for relationships such as a Dialog trigger’s `aria-controls` and a Field label’s `for`. You usually do not need to supply them.

Pass an explicit `id` when something outside the component needs to refer to a part. On the server, render order matters: if a Field label renders before a control with your ID, the label initially uses the generated ID. Hydration updates the reference to yours. The same applies to Dialog triggers, titles, and descriptions.

Use classes or data attributes for styling, rather than generated IDs.

## Give Each Request Its Own State

The server runs your modules once and reuses them for every request. Create app state inside a component and share it through context, so each visitor gets their own copy. [State and Events](./state-and-events#share-state-across-components) shows how.

Popups render in place, so your server layout doesn't need a portal root. [Popups](./popups) covers containers; [Forms](./forms) covers submission and validation.
